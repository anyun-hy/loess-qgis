# 选择 Fragmentation V3.3（2026-08-26）

## 决定

- V3.1—V3.4 的实验结果中选择 V3.3；
- 主干只接收 V3.3 规则系统、候选执行器和对应测试；
- V3.1、V3.2、V3.4 的代码、测试和实验脚本只保存在
  `research/fragmentation-v31-v34` 的提交历史；
- Fragmentation V3 继续作为生产方案，直到 V3.3 完成 approved Fusion 迁移、
  全量复算、部署和现场验收。

## 同域全量结果

固定范围为 140 个 Core、831,531,565 个 strict-valid 像元。

| 方案 | 动态碎片数 | 变化 |
|---|---:|---:|
| V3 | 30,239 | 基线 |
| V3.1-B | 25,983 | 比 V3 少 14.08% |
| V3.2 | 21,649 | 比 V3.1-B 少 16.68% |
| V3.3 | 7,545 | 比 V3.2 少 65.15% |
| V3.4 | 7,530 | 比 V3.3 只少 0.20% |

V3.3 相对 V3.2 还减少 14,104 个动态碎片、13,429 个组件和 291,981 条
内部边界边，动态碎片面积减少 69.65%。改变像元为 524,513，占有效范围
0.0631%。gap、overlap、outside、保护源类别损失均为 0。

V3.4 只再减少 15 个动态碎片和 202 个像元，属于安全但几乎无实际收益的
二次处理，因此不采用。

## 选择理由

V3.3 把已确认的业务规则同时纳入一个确定性裁决过程：

- 只处理满足分类别面积上限的完整小碎片；
- 区分源类别能否被吸收、目标类别能否增长和能否同类桥接；
- 单一类别包围直接选择唯一合法目标；
- 多类别包围先处理合法桥接，否则按冻结稀有度、目标概率、类别代码排序；
- 冲突 proposal 在一个全局顺序中去重和裁决；
- 保持 Core 唯一发布、预算、拓扑、单标签和完整审计硬门。

V3.4 没有引入新的业务信息，只是在相同规则和累计预算下增加第二轮，因此
结果说明当前规则已经接近自身上限。

## Git 和数据边界

实验过程分别记录在实验分支的 V3.1—V3.2、规则系统、V3.3、V3.4和V3.3
收口提交中。主干通过提取实验分支最终状态接收代码，不合并实验提交历史。

`.npy`、`.npz`、概率数据、栅格、临时 Mask、日志和缓存不进入 Git。Git 只
保存源码、配置、测试和小型结论文档。

## 接入生产前必须完成

1. 使用收口后的精确代码重新完成 140-Core 全量复算；
2. 接入 approved Fusion 完整概率和 Work Package/Core 所有权；
3. 逐像元验证 single-label、gap=0、overlap=0、outside=0 和保护源损失为 0；
4. 完成栅格、矢量组装、部署回读及 QGIS 现场验收；
5. 上述任一硬门失败时继续使用生产 V3。
